# Changelog

All notable changes to this project will be documented in this file. This project follows [Semantic Versioning](https://semver.org/).

## [16.4.3] - Unreleased

Changes from 16.4.2. First published as `16.4.3-rc.0`; tag retention added in `16.4.3-rc.1`.

### Added

- **`withCache(nextConfig)`: one call configures the whole cache.** It points `cacheHandler` at the page handler, `cacheHandlers.remote` at Redis, `cacheHandlers.default` at per-instance memory with shared tag invalidation, and sets `cacheMaxMemorySize: 0`. Set `REDIS_URL` in production and pages, route handlers, cached `fetch`, `"use cache"` and `"use cache: remote"` are all shared across instances. Without it everything stays in memory. Options: `useCache: "memory" | "redis"`, `pages: false`, and `handlers` for your own handler files. It also accepts a function-form `next.config`, and keeps a `cacheMaxMemorySize` you set yourself (with a warning if it is not 0). Runtime settings come from the environment (`REDIS_URL`, `CACHE_KEY_PREFIX`, `CACHE_REDIS=off`, `CACHE_DEBUG=1`), so they work the same under `next start`, standalone and Docker.
- **A working Next 16 page handler.** `RedisCacheHandler` is rewritten in place to the Next 16 `cacheHandler` contract. It honours `x-next-cache-tags` (implicit path tags included), soft tags, `fetch` tags and `cacheControl`, so `revalidateTag` and `revalidatePath` now invalidate pages and route handlers on every instance. Each read checks the tag records in Redis in the same round trip as the entry, so the next read on any instance sees a revalidation, with no added latency. `revalidateTag(tag, "max")` serves the page once more and regenerates it in the background. Entries are kept for `1.5 × revalidate`, capped at `expire`. The class name and constructor are unchanged, so 16.4.2 subclasses keep working. `createRedisCacheHandler(options)` builds one for a custom handler file.
- **Redis outages are absorbed.** Every handler shares one connection per process and fails fast: a command times out after 1 s, a connection that times out 3 times in a row is dropped and redialled, and startup waits at most 500 ms. A `client` you pass in is never disconnected or reconfigured: the package's own commands on it go through a proxy bounded by `commandTimeout`, and 3 timeouts in a row send the handlers to memory for 2 s at a time. While Redis is down, handlers serve from per-instance memory, each entry for at most 60 s, and log errors at most once a minute. When Redis comes back that memory is dropped. A request never fails because of the cache. The build phase never connects to Redis.
- **Distributed tag coordination for `"use cache"`**, following Next's [documented pattern](https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers#distributed-tag-coordination). Values stay in each instance's memory. `updateTags` writes the invalidation to Redis, `refreshTags` syncs it into local state once per request, and `getExpiration` reads local state only, so `revalidateTag` on one instance clears every instance's copy without a Redis call per lookup.
- **Entries scoped by build ID.** A deploy never serves the previous build's pages or RSC payloads. Tag records are shared across builds, so between 16.4.3 builds a revalidation during a rolling deploy reaches both.
- **A binary entry format (v2).** Bytes are stored raw instead of base64 JSON: about 25% less Redis memory and network, and a page shell `get` about 40% faster.
- **`flushCache({ scope })`** deletes the current build's keys (`"build"`, the default) or everything under the prefix (`"all"`) with SCAN + UNLINK, Cluster included, and empties the calling process's in-memory stores. It refuses `scope: "all"` with an empty key prefix. Put it behind your own authenticated route; the package ships no endpoint.
- `createRemoteCacheHandler`, `createLocalCacheHandler` and `MEMORY_ONLY_TAG` (keeps an entry out of Redis) for custom handler files. `createRemoteCacheHandler` takes `defaultTTL`: the seconds to keep an entry whose `expire` is infinite (default 24 hours, at most 365 days; any other value than a finite number greater than 0 throws when the handler is created).
- **`closeCache()`** lets a test run, script or CLI exit: it closes every Redis connection the package opened in the process, empties its memory stores and drops its tag state, after sending revalidations Redis has not acknowledged one last time. A revalidation Redis still refuses is kept, applied by this process and sent when the handlers are used again, rather than lost. It never fails because Redis is down, is safe to call twice and never closes a `client` you passed in. Handlers created before it reconnect on their next call, onto one new connection (the deprecated `createCacheHandler` does not; create it again). For a test suite: `afterAll(() => closeCache())`.
- **Your own logger.** `setCacheLogger(logger)` (in `instrumentation.ts`) sends every warning, error and `CACHE_DEBUG` line to a logger with `error` and `warn` (and optionally `info`, `debug`) methods (winston and `console` as they are; pino and bunyan through a one-line adapter, shown in `docs/operations.md`); a custom handler file can pass `logger` to `createRemoteCacheHandler`, `createLocalCacheHandler` or `createRedisCacheHandler` instead. Without one, the console gets the same lines as before. Errors stay rate-limited, logged errors, objects and URLs are scrubbed of credentials (see Security), and a logger that throws never fails a cache call.
- `createCacheHandler` gains the shared connection, the outage fallback and these options: `client`, `memoryFallback`, `fallbackTTL`, `commandTimeout` (default 1000 ms; 16.4.2 had no command timeout), `defaultTTL`, `tagTTL`, `errorLogIntervalMs` and `suppressIsrWarning`. It keeps the 16.4.2 key layout and entry format.
- CI runs Next.js's own caching suites through its deploy-test harness, with two instances behind a proxy, and fails on any suite that passes on plain `next start` but not with the package (`tests/next-deploy/README.md`). A real-Redis outage suite runs on Redis 7 and Valkey 8, and the e2e app now runs two instances against one Redis and stops Redis mid-run.
- CI: the `e2e-elasticache` job runs against Redis with in-transit TLS and an auth token; the daily canary run fails (and opens an issue) when a canary breaks; and a PR whose package major.minor is ahead of Next's latest stable release fails, as does a release workflow that picks a version npm has already seen.

### Changed

- **A smaller, fixed memory budget.** The package's in-process caches could hold about 336 MiB per process; they now hold at most 98 MiB, and 34 MiB while Redis is healthy: `"use cache"` values 32 MiB (was 50 MiB), memory-only and no-Redis page and `"use cache: remote"` entries 16 MiB each (were 64 and 50 MiB), the outage copies of each 16 MiB (were 64 and 50 MiB), and entry tag lists 2 MiB measured in bytes (was 8 MiB counted in tags). Keys now count toward a store's size. An entry larger than its store's cap is not kept in memory; without Redis that means a page over 16 MiB is rendered each time. No option was added. See "Memory" in `docs/operations.md`, including pod sizing.
- **Tag records in process memory are bounded like Redis's.** A record past the retention horizon (365 days plus 10 s after its later time, flush barriers excepted) is no longer loaded by the first sync or a read, and those held are dropped at most once a minute. The deprecated `createMemoryDataCacheHandler` and `MemoryCacheHandler` keep at most 10,000 tag records; past that the oldest half goes and entries older than those records are treated as invalidated.
- **The cache starts cold on upgrade.** The new layout is `<prefix><buildId>:page:` / `:data:`, plus two tag keys, `<prefix>tags` and `<prefix>tag-index`. The 16.4.2 page handler's keys (`nextjs:cache:*`, `nextjs:tags:*`) are no longer read and expire on their own. `createCacheHandler` keys are unaffected. Because of this, a revalidation handled by a 16.4.2 instance (through `createCacheHandler`; 16.4.2's page handler did not apply `revalidateTag` on Next 16 at all) does not reach 16.4.3 instances while both serve during a rolling deploy, and the reverse: deploy this upgrade with recreate, or revalidate once from 16.4.3 (for example `revalidatePath("/", "layout")`) after the last 16.4.2 instance is gone (see `docs/migrating.md`).
- **`createCacheHandler` serves stale and survives failover.** It returns an entry until its `expire`, not its `revalidate`, so Next serves it while regenerating in the background (16.4.2 deleted it at `revalidate`), and does not store an entry that has already expired. Its Redis client reconnects forever with a backoff capped at 5 s (16.4.2's ElastiCache client gave up after 3 tries, disabling the cache until a restart) and fails commands fast while disconnected. Redis errors are logged, rate-limited, instead of swallowed. A `get` waits for an in-flight `set` of the same key in the process. Tag records expire after `tagTTL` (366 days) and entry TTLs are capped at it, so a record always outlives the entries it can invalidate. A tag's `expired` deadline that predates an entry no longer deletes it, as in Next. An entry's tags are checked concurrently.
- `createCacheConfig` / `createCacheConfigWithProfiles` take `isrHandlerPath` as optional and emit `cacheHandler` only when it is passed.
- Importing the package no longer requires `ioredis`; 16.4.2 loaded it at import through `RedisCacheHandler`.
- `jsonReplacer` / `jsonReviver` store a Buffer as base64 at every nesting level, not only at the top.
- Connection options that refer to themselves (a `redisOptions` object containing itself) throw `Redis connection options must be serializable: … refers back to an enclosing object` when the handler is created, instead of overflowing the stack.
- The page handler's `get` no longer returns `age`. Next computes staleness from `lastModified` and `cacheControl`.
- A `RedisCacheHandler` created without a `redis` option reads `REDIS_URL` and runs in memory when it is unset. In 16.4.2 it connected to `localhost:6379`. Its `tagPrefix` option is ignored, and `defaultTTL` defaults to 365 days and applies only to entries with neither `revalidate` nor `expire`. A fractional `defaultTTL` is rounded up to whole seconds, and any other value than a finite number greater than 0 throws when the handler is created.
- **No cached value is kept or served past 365 days** (`cacheLife("max")`'s `expire`), whatever its profile or `defaultTTL`. Every store (Redis, the `"use cache"` memory, memory-only entries and the outage fallback) caps the age on write and checks it on read.
- **Old tag records expire or are pruned.** Redis 7.4+ and Valkey 9+ use hash-field TTLs; standalone servers also run a bounded atomic prune in the background. A record stays until 365 days plus 10 seconds after the later of its update and delayed expiration deadline. Flush barriers stay permanently. Cluster without field TTLs retains the old grow-until-flush behavior and logs a rate-limited warning. The index on a supported Cluster can retain members whose fields expired. Key layout and entry format are unchanged.
- Build output with no surviving stamp can come back after its tag record is pruned if the same build has served for over 365 days after the tag's last invalidation. Redeploy or flush within a year; missing-stamp behavior is unchanged.
- A failed or skipped tag check is a miss, never a stale hit: `"use cache: remote"` reads its tag records from Redis with the entry, and `"use cache"` misses until its tags have synced since the last (re)connect or failed sync. A revalidation made while Redis was unreachable is sent when it is back. The `"use cache"` tag sync pages the index by score, so a tag revalidated mid-sync can no longer make it skip another, and a writer with a fast clock can no longer make others miss updates. A reply that arrives after its command timed out no longer counts as a recovery. A tag write Redis refuses while connected (`OOM`, `READONLY`, a timeout) is retried by the next sync, and `revalidateTag` does not resolve before Redis has acknowledged its tag.
- `flushCache` no longer keeps a script, test or CLI alive. Called before any handler has opened the Redis connection, it opens a client of its own and quits it before returning, also when the flush fails, instead of leaving the shared client open (which kept the process running and, once Redis was gone, retrying `ECONNREFUSED` forever). With its own client it throws if Redis did not take the flush record, since nothing would send it again. In a server whose handlers are connected it uses their client as before.
- `flushCache` on a Cluster retries a key answered with `-MOVED` / `-ASK` (a slot migration) through the Cluster client instead of throwing mid-flush. Keys that still fail are reported as `{ deleted, partial: true, failed }` with a warning. `scope: "all"` deletes everything under the prefix, including 16.4.2's `nextjs:cache:*`, `nextjs:tags:*` and `nextjs:data-cache:*` keys and any other app's keys sharing the prefix.
- **Prerendered routes are served from the build output again, also after a restart.** A custom `cacheHandler` replaces Next's file system cache, so prerendered pages and route handlers (sitemaps, robots, manifests) were rendered again on their first request. On a miss the page handler now reads the build output through Next's own `FileSystemCache`, under Next 16.4's route cache keys as well as the older ones, with the usual tag check (a revalidation since the build wins), and writes it to Redis with `SET NX`. A dynamic route's prerendered fallback shell (partial prerendering, e.g. a page that awaits `params`) is served too, with the route's `fallbackRevalidate` / `fallbackExpire`. Build output is not served while Redis is down. A route with a revalidate period is served from it only within `1.5 × revalidate` (capped at `expire`) of the build, so a regenerated page whose key expired never falls back to its build-time copy. `flushCache` records the flush as a tag revalidation, so build output older than it is not served again, even after `scope: "all"` deleted the tag records. The build time comes from `cache-handler-build.json`, which the page handler writes into `.next/server` during `next build` when static generation starts (so a long compile does not use up the window), never from file mtimes. Ship it with `.next`: without it, only `revalidate: false` routes with no tag record at all are served from the build output.
- **Route handlers with sequential `"use cache"` calls are prerendered again.** With `cacheComponents`, Next aborts a prerender that reads the clock through `Date`, and the handlers did, so such a route was silently built as dynamic. The handlers now never read `Date` during a prerender, also when the package resolves a different copy of `next` than the app or is used before Next has started.
- **Instances agree on time.** Revalidations and entries are compared on wall time across instances, even when a long-running instance's monotonic clock has drifted by seconds; what remains is the wall-clock skew between machines, which the tag sync already allows for (5 s).
- **Edge middleware no longer crashes.** Next bundles the page handler into the edge middleware; importing the package there called `createRequire` and failed every request with a 500. The handler entries now import no Node built-in at all (Turbopack's edge build fails on merely loading one): built-ins come from `process.getBuiltinModule` on first use, and on the edge runtime the handlers are no-ops (every read a miss). This needs Node.js 22.3 or later (`engines` was `>=22.0.0`).
- Two revalidations sent at the same moment no longer make one of them send an empty `HSET`, which Redis rejects.
- **A connection dropped for timeouts no longer flaps forever.** ioredis resent the timed-out commands after each reconnect, and the timeout watchdog counted each resend as a new timeout, so with 3 or more commands stalled at once every reconnect was dropped again and Redis never came back. Commands are no longer resent (`autoResendUnfulfilledCommands: false`), and each command is counted once.
- Page entries store the duplicated `/_full` RSC bytes once, about 20-26% smaller.
- **A revalidation can no longer be undone by an older one arriving late.** Tag records are merged in Redis by a single-key Lua script, in the order the revalidations were made rather than the order they arrive, and the tag index uses `ZADD GT`. Before this, an older write delayed in transit replaced a newer acknowledged one, and an instance started afterwards served an entry the newer revalidation had invalidated. This needs Redis 6.2+ (or Valkey) with scripting allowed.
- Pages Router (`PAGES`) values now honour their `x-next-cache-tags` header, in Redis and from the build output, as Next's own file system cache does.
- **Large entries are stored compressed.** Page and `"use cache: remote"` entries of 16 KB and more are written with Brotli (quality 4, off the event loop) as entry format v3, typically 5 to 15 times smaller: a ~200 KB page entry stores in ~14 KB, a 5 MB search page in ~1 MB. Entries over 64 MB are stored uncompressed, and a compressed entry claiming more than 64 MB is a miss, so a corrupt entry cannot make a read inflate hundreds of megabytes. Both v2 and v3 entries are read; a corrupt or unknown entry is a miss. `CACHE_COMPRESSION=off` writes uncompressed v2.
- `connectTimeout`, `socketTimeout` and `maxConsecutiveTimeouts` are `CacheOptions`, so every factory (`createRemoteCacheHandler`, `createLocalCacheHandler`, `RedisCacheHandler` / `createRedisCacheHandler`, `createCacheHandler`) and `flushCache` take them. `withCache`'s built-in handlers read only the environment; pass the options in your own handler files (`withCache({ handlers })`). Handlers given different settings for the same server open separate connections and keep separate tag state; the package now logs one warning when that happens.
- `CACHE_DEBUG` (or `debug: true`) logs each value's size on `get` and `set` for the page, remote and `"use cache"` handlers: `bytes`, plus `encodedBytes` (the Redis payload) for page and remote entries.
- `withCache(config, { pages: false })` keeps a `cacheHandler` already in your config instead of throwing. With pages enabled it still throws.
- `createCacheHandler` with a Redis-family backend logs a one-time production warning that it does not cover pages, pointing at `withCache`. It is skipped when the package's page handler (`RedisCacheHandler`) exists in the same process (checked on first use); opt out with `suppressIsrWarning: true`.
- **Sizing:** a page read now sends one `HMGET` of its tag records alongside the entry's `GET`, in the same round trip (2 commands instead of 1; 3 in 2 round trips the first time a process reads an entry it did not write). A revalidation is 1 `EVALSHA` + 1 `ZADD GT`, and the `"use cache"` tag sync reads only the tags changed since the last one; nothing runs `HGETALL`. Every tag record lives in one hash per prefix (100,000 tags take about 23 MB), so tag reads all go to one key: about 2% of a core at 2,000 page reads/s, mattering around 50,000/s. See Sizing in `docs/redis.md`.
- **`flushCache` on a Cluster can no longer hang.** It scans each master through that master's own client, which the `commandTimeout` proxy over a client you pass in did not cover, so a master that stopped answering left the flush (and the route calling it) pending forever. Each master's commands and pipelines are now bounded by `commandTimeout` too, and a flush that fails part-way throws, saying some keys may already be deleted; run it again. Your client is never changed or disconnected.
- **A corrupt entry is a miss in every case.** A stored entry whose binary reference was negative, fractional, not a number or outside the entry was decoded into the wrong bytes (part of the entry's header) rather than treated as a miss.
- A corrupt tag record in Redis (a value that is not `<stale>,<expired>` in milliseconds) no longer makes every revalidation that touches it fail. The merge script reads it as the decoder does, a non-number as no record, and overwrites it.

### Security
- **Redis errors are logged without the command that failed.** ioredis attaches the failed command, arguments included, to a Redis error, so when Redis rejected `AUTH` (a rotated or disabled credential) the logged connection and tag-write errors carried the password that was tried, to your logger and to the console. Every warning and error line now carries errors, and each error in their `cause` chain, with only their name, message, stack and network fields (`code`, `errno`, `syscall`, `address`, `port`); objects without `command`, `password` and similar keys; other values (a `Buffer`, a class instance) as a placeholder such as `[Buffer 12 bytes]`; and URLs without their user information, up to the last `@`. Other free text in a message is not scrubbed.

### Deprecated

Still exported and still working, removed on the Next 17 line. Each has JSDoc pointing at its replacement:

- `createCacheConfig`, `createCacheConfigWithProfiles` → `withCache`.
- `CompositeHandler`, `createCompositeHandler` → built in; every handler has the memory fallback.
- `MemoryCacheHandler`, `createMemoryCacheHandler` → `withCache` without `REDIS_URL`.
- The original data cache stack: `createCacheHandler` → `withCache`, or `createRemoteCacheHandler` / `createLocalCacheHandler` in a custom handler file; `createRedisDataCacheHandler` and `createIoredisAdapter` → `createRemoteCacheHandler({ client })`; `createMemoryDataCacheHandler` → `createLocalCacheHandler`. They keep working in 16.x and are removed, or become a shim, on the Next 17 line.
- `RedisCacheHandler#close()` → `closeCache()`, which it now calls.
- The Next 14 helpers and types (`bufferToString`, `stringToBuffer`, `jsonReplacer`, `jsonReviver`, `isImplicitTag`, `calculateLifespan`, `isExpired`, `IMPLICIT_TAG_PREFIX`, `CacheHandler`, `CacheHandlerOptions`, `LifespanParameters`) → no replacement. The Next 14 value and context types → their Next 16 page cache counterparts: `CacheValue` → `PageCacheValue`, `CacheHandlerValue` → `PageCacheHandlerValue`, `CacheHandlerContext` → `PageCacheHandlerContext`, `CacheHandlerGetMeta` → `PageCacheGetContext`.
- `MemoryCacheHandlerOptions` and `CompositeHandlerOptions`, with their handlers.

### Docs

- `cacheMaxMemorySize: 0` is described correctly: it has no effect on caching with `withCache`, since it sizes Next's own file-system page cache and built-in `"use cache"` handler, which Next does not use once the handlers are set. The `withCache` warning for a non-zero value says so instead of claiming Next would serve revalidated pages.
- The README is rewritten around `withCache` as a short landing page: quick start, configuration, how the package is tested against Next.js's own suites, backends and a migration summary. The reference material is in `docs/`: `how-it-works.md` (what goes where, tag coordination, pages and route handlers, the outage behaviour), `operations.md` (flushing, closing, logging), `custom-handlers.md`, `migrating.md` (from 16.4.2, from `RedisCacheHandler` subclasses, and from `@fortedigital/nextjs-cache-handler` / `@neshca/cache-handler`), and the key layout and sizing for operators in `redis.md`; the export and deprecation tables are in `api-reference.md`.
- JSDoc import paths point at the package root, and `createCacheHandler`'s documented `keyPrefix` default is the real one, `nextjs:data-cache:`.

## [16.0.0] - 2025-11-18

### Added

- `CHANGELOG.md` to track releases.
- Test coverage for the zero-config data cache factory, ensuring Redis/Valkey env handling works across backends.

### Changed

- Promoted the package from `16.0.0-alpha.6` to the first stable release aligned with Next.js 16.
- Updated the zero-config factory to load `ioredis` safely in pure ESM projects and to honor TLS/password options (including AWS ElastiCache env vars).
- Removed the unused CommonJS export entry; the package is now explicitly ESM-only.
- Reworked documentation (README, installation guide, Redis guide, package README) to reflect the modern APIs, supported backends, CI guarantees, and the motivation for this new repo.

### Fixed

- Redis/Valkey/ElastiCache handlers now apply `REDIS_PASSWORD`, `ELASTICACHE_*` env vars, and custom TLS options so production deployments connect successfully.
